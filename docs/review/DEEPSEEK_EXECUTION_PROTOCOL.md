# PCS 项目逐步修改与审阅交接协议

适用项目：TMS320F28374S、T 型三电平三相 PCS。此文件是给后续代码执行者 DeepSeek 的工作指令，也是项目所有者与 Codex 审阅者之间的交接格式。文档和代码一同保存在 Git；**文档内容不构成板上运行许可**。

## 0. 固定基线与角色

- 原始代码备份基线：`57f94362aab18df739b40f7109b1e6987745224c`（`refactor/batch0.5` 上的 2026-10-29 审阅与修复提交）。无论后续分支怎样移动，所有总差异都以此完整 SHA 为起点。不得重写、覆盖或强推该基线。正式开始修改前，项目所有者应在 Git 上为它建立固定标签 `pcs-baseline-20261029`，并核对标签所指 SHA 等于上述值；DeepSeek 不得代建或移动该标签。
- DeepSeek：一次只实施一个明确的变更单元，给出改动意图、代码差异、验证证据和剩余风险，收到本步审阅结论前停止下一步。
- Codex：作为独立审阅者，逐步核对设计意图、前后差异、芯片寄存器依据、构建/测试证据及安全影响。不能由静态证据判断的事项标为“待板上验收”或“需项目所有者裁定”，不得猜测通过。
- 项目所有者：决定未定的硬件事实、控制策略、保护阈值、上电/并网许可及争议事项；负责最终接受、合并和发布。DeepSeek 与 Codex 不得把自己的推断当成这些决定。
- Git 权限：DeepSeek 只在隔离工作分支准备本步变更；是否创建/推送提交由项目所有者当次指示。未经明确安排不得合并、改写基线、推送主分支或删除既有工作。Codex 只审阅，不替项目所有者提交或推送。

开始前先核对 `git rev-parse HEAD`、工作分支、`git status`。当前仓库有 CCS 生成的 `Debug/` 改动及工程元数据改动；不得把它们混入功能变更，也不得擅自清理。每一步报告应注明本步基点 `base_sha`、变更后 `head_sha`（未提交时用工作区差异）与原始基线 SHA。若基点发生意外变化，先停止并报告。

## 1. 设计边界

1. 分层意图：`Broad` 管板级配置表，`Drivers` 管芯片寄存器和底层驱动，`Platform` 管可复用组件，`User_App` 管整机与控制策略。更改层间职责须单独提出理由，不能顺手扩散。
2. 系统及 INV/PV/BUS 驱动状态机在后台低速任务运行。三个功率级的目标开关频率均为 20 kHz；快速控制最终应各以 20 kHz 执行，且错峰安排必须有时序证据。当前 ZERO→CLA Task1→CPU ISR 承载 INV，PRD→CLA Task2→CPU ISR 承载 PV 与 BUS 采样；**BUS 20 kHz 闭环尚未实现**。不得把 PWM 频率等同于闭环执行频率。
3. INV 是 T 型三电平单极性调制：正半周 S1/S3 互补，S2 常导通、S4 断开；负半周 S4/S2 互补，S3 常导通、S1 断开。用户已确认 GPIO 对应关系；ePWM、AQ/DB、同步、ADC/CLA、TZ 仍须逐项验证。未经门极波形验证，不得声称换相安全。
4. 离网电压/电流控制、母线前馈、重复控制及并网电流环仍是待选设计。当前并网自动合闸锁禁；缺少同步许可、电流环和实测参数时不得解除。BUS ePWM8 当前应保持 TZ OST 双路关断，直到独立保护与控制验收完成。
5. 保护阈值、驱动/比较器有效极性、L/C、采样增益、传播延时等未经项目所有者确认的硬件事实必须列出问题，不得自行编造数值。任何故障都不能由普通占空比写入解除硬件锁存。

阅读顺序：先读 [修复状态](2026-10-29/05_fix_status.md)了解现状，再读 [当前逻辑](2026-10-29/01_current_logic.md)、[缺陷基线](2026-10-29/02_defects.md)和 [验证矩阵](2026-10-29/03_validation_plan.md)。缺陷基线的行号和“当前”是修复前快照；必须对照最新源码重新定位。

## 2. 严格的单步循环

每步必须经过以下关口，不能把多个修复合成一个无法辨别的“大优化”。

1. **申请本步**：写明一个问题编号或验收编号、预期行为、拟改文件、可能影响的功率输出、验收方式和当前缺失的信息。先给 Codex 审阅意图；若需要项目所有者确定硬件事实，停在这里。
2. **实现本步**：只改本步所需文件。保持外部驱动禁止和既有故障锁存；不能为让测试通过而绕开保护或让应用自动发波。与本步无关的重构另开下一步。
3. **交付差异**：提供 `base_sha`→本步结果的完整文件列表和 `git diff --stat`、关键 diff；另提供从 `57f94362…` 到当前结果的累计差异摘要。说明每处修改前的行为、修改后的行为及其硬件依据。不能只给自然语言总结。
4. **提供验证证据**：至少执行与改动匹配的构建/静态检查，并引用验证矩阵 ID。实板测试需附寄存器读回、仪器条件和波形/日志；未执行就写“未测”，不能写“通过”。记录工具链版本、配置、命令、退出码与失败输出。
5. **等待审阅**：Codex 给出“通过进入下一步”“返工后重审”或“提交项目所有者裁定”。审阅者须检查本步相对前一已接受版本的差异，且核对相对原始基线的累计变化。没有明确“通过”不得开始下一步。
6. **记录结论**：DeepSeek 按审阅意见修改时，仍须提交新的差异和复验结果；已接受步骤的证据与结论保留在交接记录中。若前一步被推翻，依赖它的后续步骤暂停。

若 DeepSeek 需要改变已批准的设计意图，先提交“设计变更申请”而不是直接编码。Codex 无法确定时必须明确指出判断所依赖的未知量、可选方案及各自风险，交项目所有者裁定；默认状态保持禁能。

## 3. 每步交接报告模板

在 Git 中以独立 Markdown 文件或提交说明交付。文件名建议 `docs/review/steps/NN-简短主题.md`，一个步骤一个文件。

```markdown
# 步骤 NN：主题

- base_sha：前一已接受版本的完整 SHA
- head_sha：本步提交的完整 SHA；未提交则写“工作区待审”
- original_baseline：57f94362aab18df739b40f7109b1e6987745224c
- 对应缺陷/验收 ID：Fxx / Axx、Bxx、Cxx、Dxx、Exx
- 状态：待审 / 返工 / 已接受 / 需项目所有者裁定

## 意图与边界
问题、设计目标、拟改层次、明确不改的相邻功能；若变更保护或发波路径，写出上电默认态和故障态。

## 修改前后
文件与函数；原行为→新行为；关键寄存器位和手册章节；本步 diff 链接或 `git diff base_sha..head_sha` 输出。

## 验证
构建命令/工具链/退出码；测试 ID、输入条件、预期、实测、日志/波形路径；未测项明确写“未测”。

## 风险与请求裁定
残留问题、可能回归、所需硬件信息；需要项目所有者回答的问题列为具体可判定事项。

## 审阅结论（由 Codex 填写）
通过进入下一步 / 返工后重审 / 提交项目所有者裁定；理由、证据、阻断项。
```

若通过 Git 交换，提交应保持**一项问题一个可审阅提交**，报告写明提交 SHA；比较命令以实际 SHA 为准，例如 `git diff <base_sha>..<head_sha> -- Broad Drivers Platform User_App CMD main.c`。不要把 `Debug/`、`tmp/`、工具缓存或无关格式化加入 diff。后续合并由项目所有者完成。

## 4. 推荐执行次序与关口

| 次序 | 本步目标 | 进入下一步的最低证据 |
|---|---|---|
| 1 | 静态构建与配置复核（A01–A03），核对 CLA 消息 RAM、ADC SOC、PWM 同步及 X-BAR/TZ | 可重现的干净构建、MAP、配置表与寄存器预期逐项一致；发现的新问题单独登记 |
| 2 | CLA/ADC/ISR 最小链路（B01–B05），包括两批采样和 20 kHz 截止期 | 驱动禁止下的序号、EOC、CLA/CPU时戳与 overflow 证据；无样本混批、无漏拍 |
| 3 | MUX 与失联保护（B06–B07），然后 BUS 默认关断和各保护源单独注入（D01、D06、D07） | 实际输入极性、作用范围、传播延时及复位安全态的板上证据；未获硬件数据先交项目所有者 |
| 4 | INV/PV 波形、同步装载与 T 型换相（D02–D05） | DSP 引脚和外部门极两侧波形；正负半周、过零、边界延迟和故障后的安全态均符合批准标准 |
| 5 | SCI/Modbus、CAN、SPI、FRAM/I2C（C01–C07） | 逐协议正常/异常/边界测试；错误后可恢复且无错误命令执行 |
| 6 | BUS 闭环与离/并网控制设计，再进入低压限流功率测试（E） | 项目所有者确认硬件模型、阈值、同步许可和控制方案；先单功率级，后组合运行 |

上表是依赖顺序，**不是一次性开发清单**。每行内部仍拆成单步报告、单步审阅。静态测试与驱动禁止下的检查可以先进行；没有板上证据的阶段不得在报告中标为已验收。完整测试条件见 [验证矩阵](2026-10-29/03_validation_plan.md)。

## 5. 审阅的判定准则

Codex 每步至少检查：设计意图是否仍满足；文件层次与接口是否合理；相对前一接受版本及原始基线的差异是否完整；20 kHz 频率、采样批次与最坏执行时间是否有证据；安全默认态、Trip 锁存和故障恢复是否被削弱；新测试能否检出原故障；报告是否把“编译通过”“静态推断”“板上实测”分开。

**通过**仅表示该步在已声明的证据范围内达到标准，不表示整机可上电运行。证据缺失、硬件事实不明或安全作用范围无法判断时，结论必须是“返工”或“提交项目所有者裁定”，并列出下一步所需的最小信息。项目所有者给出裁定后，DeepSeek 更新设计记录和本步实现，再重新审阅。
